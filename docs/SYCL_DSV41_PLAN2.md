# SYCL plan for the DeepSeek engine (dsv41), round 2: what is left

Round 1 (see [SYCL_DSV41_PLAN.md](SYCL_DSV41_PLAN.md)) moved the quant kernels: `tq`, `gguf` and `iq` compile for SYCL behind the opt-in `STRATA_SYCL_DSV41`, and a parity test on this PC's Intel Arc Pro B60 printed MATCH for 4096 of 4096 BF16 values against the CPU reference. The tensor-core blocks inside two kernels are scalar stand-ins today, and the engine cannot run yet. This plan covers the rest, shaped by a research round over the local trees on this machine: `~/XeStrata` (the Strata Xe port), Strata's own `sycl/` project, `~/llama.cpp`, and the two SYCL toolchains.

## What this round found

**The matrix path works on this machine's chip.** A small `joint_matrix` probe (fp16 A 8x16 row-major, fp16 B 16x16 col-major, float accumulator 8x16, sub-group 16, `grf_size<256>`) compiled green — exit 0 — four ways on this PC on 2026-10-24: oneAPI icpx 2026.2 JIT, icpx AOT for `bmg-g21`, self-built intel/llvm DPC++ 7.2.0 JIT, and that one AOT for `bmg-g21`. Nothing about Battlemage blocks the tile itself. The runtime header has no compile-time specialization for `bmg_g21` (only DG2 and PVC); kernels ask the device at run time instead, the way XeStrata does. Device-run proof is the first hillclimb step, not a plan claim.

**There is a pattern to copy, already in this repo.** `sycl/src/prefill/xmx_moe.dp.cpp` (lines 64-113) is the canonical shape: float accumulator, `joint_matrix_load` from shared local memory padded by 8, K-steps of 16, `joint_matrix_mad`, store to global with row-major layout, `grf_size<256>` properties, `[[sycl::reqd_sub_group_size(16)]]` under `STRATA_XMX_SG16` (set by CMake when `STRATA_SYCL_AOT` is `bmg-*` or `lnl*`, `sycl/CMakeLists.txt` lines 40-41). On Xe2 its work-groups are 128 lanes (8 sub-groups of 16). `iq_kernels.dp.cpp` adds `ext_intel_packed` for packed weight tiles; `xmx_int8_bench.cpp` shows int8 tiles of K=32 with int32 accumulators and a `joint_matrix_apply` step for per-block scales — that is how MXFP4/IQ scales fold in.

**XeStrata proves the same shapes in a shipping engine.** Its hand-written kernels: `xmx_gemm.cpp` (fp16/bf16, 8x16x16, SG16, GRF256, AOT for `bmg_g21`), `iq_mmq.cpp` (int8, 8x16x32 on Xe2, grouped by expert with row-tile choice from `max_rows`/`mean_rows`, DP4A fallback), `qsa_prompt_attn.cpp` (fp16, 16x16x16, SG16), and a per-device capability gate built from the runtime matrix combinations query, with `STRATA_NO_BF16_MMA` / `STRATA_NO_INT8_MMA` env switches. It gates capability checks before launching and falls back when the device lacks a combination. Measured numbers for this PC, from its `--hw-bench` on 2026-10-17 (contrib-llvm build, xe0.1.44.1-1): launch 5.9 µs, 64 KiB copy 11.1 µs, H2D 14.44 GB/s, D2H 14.30 GB/s, two GPUs reading at once 14.2 GB/s each, peer copy GPU→GPU 8.44 GB/s against 6.58 GB/s through host RAM, RAM read 38.19 GB/s on 8 threads, SSD 4.98 GB/s. No tokens/s numbers for the B60 exist in any file — none for dsv41 either, so every speed claim in the phases below must come from a run on this PC.

**The IQ4_NL kernel we refused has a drop-in template.** llama.cpp (MIT) already runs IQ4_NL on SYCL: `ggml/src/ggml-sycl/dequantize.hpp` lines 1588-1605, 32 work-items per 256-value group, 8 sub-blocks of 32 values, one fp16 scale per sub-block, table lookup, no shared memory, no subgroup intrinsics — embarrassingly parallel. Its `kvalues_iq4nl` table is the same 16 values as Strata's (`-127,-104,-83,-65,-49,-35,-22,-10,1,13,25,38,53,69,89,113`; compared from both trees on this PC). Q4_K/Q5_K/Q6_K/IQ4_XS there match the same GGUF layout Strata uses, but Strata's converted kernels already cover those five through `dq_rows`; only IQ4_NL is missing. llama.cpp's MXFP4 path (`dequantize_block_mxfp4` plus an `e8m0 → float` step that shifts the byte 23 bits) confirms our E4M3/E8M0 decode approach. Nothing in ggml-sycl covers Strata's trellis/APR format; that stays in-house. Its dual-GPU design splits tensors by rows across devices outside the kernels; all kernel offsets are 64-bit.

**The BLAS migration is small and has a precedent.** `ds4_model.cu` has 3 cublas calls (2 `cublasGemmEx` fp16→fp32 at lines 2910/2924, 1 `cublasSgemm` fp32 at 2937); `ds4_vision.cu` has 10 more (all fp16/bf16→fp32 or bf16, via one `gemm()` wrapper at line 185). That is 13 calls, all plain gemms with transposes — no cublasLt, no fused epilogues. oneMKL's SYCL `gemm` and `gemm_batch` cover them 1:1 (type combinations float, half→float, bf16→float confirmed from `/opt/intel/oneapi/mkl/latest/include/oneapi/mkl/blas/` headers, static reading). Strata already has two precedents: `include/strata/hip_compat/cublas_v2.h` (a macro shim that makes CUDA cublas names compile on HIP) and `sycl/src/prefill/gemm.dp.cpp` (`dpct::blas::gemm` over oneMKL, with a 4 GiB operand staging workaround). `cublasSetWorkspace` has no SYCL equivalent — dpct itself marks it redundant; oneMKL manages its workspace. The router gemv kernels (`gemv_f16`, `gemv_f32`, `gemv_f16_rows`) and the vision softmax are custom kernels, not BLAS calls; they need SYCL ports, not library mapping.

**Toolchain choice.** oneAPI 2026.2 (`icpx`, oneMKL 2026.1) stays the build for dsv41 SYCL: the current target compiles green with it, and oneMKL headers only exist there. The self-built intel/llvm tree (DPC++ 7.2.0) compiles the matrix probe too and carries XeStrata patches, but has no oneMKL, so it is an option for AOT builds, not the default. AOT device name on this machine is `bmg-g21` (alias spelling `bmg_g21` in the driver; PCI addresses change between boots, so device selection must re-read PCI each start).

**Engine hygiene learned from XeStrata on this PC.** Killing the engine mid-cleanup leaves the GPU in a `PAGEFAULT → CAT error → DEVICE_LOST` state that blocks later starts; stop with SIGTERM and wait. GPU reset needs root. Use the probe pattern (`sycl-ls` plus a small device-info program) before blaming a kernel.

## The phases, in order

Each phase lands as its own commit, keeps `STRATA_SYCL_DSV41` opt-in, and keeps the default CUDA/HIP path byte-identical. The parity harness (`ds4_parity`) is the gate for every kernel phase; new numbers only from runs on this PC.

**Phase A — matrix tiles in the two tensor-core kernels.** Rewrite `mx_set_tc_kernel` (`ds4_gguf.dp.cpp:1087`) and `set_tc_kernel` (`ds4_iq.dp.cpp:1046`) with `joint_matrix` following `xmx_moe.dp.cpp`: dequant to fp16 into padded SLM, SG16 tiles under `STRATA_XMX_SG16`, float accumulators, scales folded with `joint_matrix_apply` (as the int8 bench does). Gate: compile green with `STRATA_SYCL_AOT=bmg-g21`, and `ds4_parity` still prints MATCH 4096/4096. Then one timed run, scalar vs tiles, on the B60 — report both with the build that produced them.

**Phase B — IQ4_NL.** Add a dedicated kernel for the 32-value block shape, from the llama.cpp template with Strata's BF16 output, and drop the refusal in `dequant_rows`. Gate: parity against the CPU reference for IQ4_NL rows on device.

**Phase C — BLAS and helpers.** Add `include/strata/sycl_compat/cublas_v2.h` mirroring the HIP shim: `cublasGemmEx` → `dpct::blas::gemm` (oneMKL), handle → descriptor, `SetStream` → queue, `SetWorkspace` → no-op. Port the three gemv kernels and the vision softmax as SYCL kernels. Gate: everything compiles, gemv parity against CPU on device. This phase touches no engine code.

**Phase D — engine wiring.** Build `ds4_model.cu` for SYCL behind the same opt-in flag, run one small DeepSeek pack on one B60, measure prefill and decode tok/s (there is no B60 baseline — this is the first number, stated with its build and date). Follow the SIGTERM/PCI discipline above when stopping.

**Phase E — tuning and reach.** Occupancy: replace the current one-work-group-per-launch default with measured work-group sizes (start from 128 lanes as `xmx_moe` uses, tune with timings). Then dual-GPU expert placement using peer access (measured 8.44 GB/s GPU→GPU on this PC beats 6.58 GB/s host relay), the `peer_experts` stub in the port is the hook. Vision, exl3 and sampler follow as separate increments.

## Limits of this plan

- Static findings above (oneMKL type combinations, llama.cpp kernel shapes, cublas inventory) are marked as reading of code; the probe compiles, table comparison, and the round-1 parity run are measured on this PC.
- Run-time device confirmation of `joint_matrix` on `bmg-g21` is Phase A, not a claim here.
- No B60 tokens/s exists for dsv41 anywhere today; Phase D produces the first.
