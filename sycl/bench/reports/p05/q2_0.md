# P0 #5: Q2_0 (ggml_type 42) pre-unpack feasibility

Q2_0 is the smallest dense K-quant (2 bits/element). This report asks whether the Q6_K
pre-unpack trick (P0 #2 avenue 1, exp 27/28) transfers: does a one-time `Q2_0 -> signed-byte`
transform, decoded by a no-bit-unpack load+dp4a kernel, buy anything near the ~2x the Q6_K
dense decode got? Source-transcribed, line-cited only; no measurements in this file.

## 1. Q20Block layout and the current decode

The weight block is defined in `sycl/src/kernels/cuda/native_mmvq.dp.cpp`:

```cpp
struct Q20Block {
    sycl::half d;
    uint8_t qs[16];
};
```
(native_mmvq.dp.cpp:68-71) — an `fp16` scale plus 16 payload bytes, 2-bit packed, 64 elements
per block. The static_assert pins it: `sizeof == 18 && alignof == 2 && offsetof(qs) == 2`
(native_mmvq.dp.cpp:114).

The dense decode kernel `native_q2_0_mmvq_kernel` (native_mmvq.dp.cpp:333) runs `q2_q8_dot`
per block (native_mmvq.dp.cpp:307), which is the unpack-in-kernel path. It loads the 2-bit
payload through `int16_t` reads (the block is only 2-byte aligned, so 16-bit loads rather than
naturally aligned 32-bit; native_mmvq.dp.cpp:310), then, per 32-element chunk, expands each
16-bit word with TWO `byte_level_permute` passes per element half:

```cpp
const int qe = dpct::byte_level_permute(0x020100ff, 0x020100ff, q >> 0);
const int qo = dpct::byte_level_permute(0x020100ff, 0x020100ff, q >> 2);
const int qx = dpct::byte_level_permute(qe, qo, 0x5140);
const int qy = dpct::byte_level_permute(qe, qo, 0x7362);
sumi = STRATA_DP4A(u, qx, sumi);
sumi = STRATA_DP4A(v, qy, sumi);
```
(native_mmvq.dp.cpp:319-324). The 2-bit codes are unpicked into signed bytes ({-1,0,+1,+2})
with these bit permutes and fed to one dp4a against each 32-bit activation word, for the block's
64 elements in `d2 * d8 * sumi` (native_mmvq.dp.cpp:327-328). So the GPU decode already has the
dp4a structure; what remains in-kernel is the 2-bit unpack.

## 2. Value formula

The value contract is settled from source in `dequant.hpp`:

> block = { fp16 d; uint8 qs[16] } = 64 elements, 18 bytes
> code {0,1,2,3} -> symbol {-1,0,+1,+2};  v = (code - 1) * d
> 4 codes per byte, LSB-first: byte j/4, bits (j%4)*2
(dequant.hpp:8-11)

The scalar dequantizer implements it exactly:

```cpp
const int byte_index = j / 4;
const int bit_offset = (j % 4) * 2;
const int code = (qs[byte_index] >> bit_offset) & 0x03;
out[j] = (float)(code - 1) * d; // code {0,1,2,3} -> symbol {-1,0,+1,+2}
```
(dequant.hpp:72-76)

So the value formula is **q2_0 = d * (2-bit code − 1)**, code in {0,1,2,3} → symbol
{-1,0,+1,+2}, one shared scale `d` per 64-element block.

## 3. Concrete pre-unpacked form

Q2_0 has a *single* scale `d` across all 64 elements (unlike Q6_K, which carries signed
per-16 scales). The 2-bit → signed-byte step is trivial: {0,1,2,3} − 1 is either a small static
table ({-1,0,+1,+2}) or a plain `- 1` arithmetic shift per 2-bit field (down to a byte-level
add, no gather). Fold `d` once per 16-element group into a 16-value block:

```cpp
struct Q20UBlock {
    float d;        // folded weight scale (same d for a Q2_0 64-block, per-16 group)
    int8_t qs[16];  // 16 signed bytes, already un-packed to {-1,0,+1,+2}
};
```

Sixty-four Q2_0 elements = four such 16-value blocks (payload is 16 bytes = one `int4`, the
same shape the `Q8_0`/`Q6_U` wide32 decoders use: `Wide32Q8::load` reads 16 bytes with
`load16_a2(b->qs + 16*l)` (native_mmvq.dp.cpp:1720-1728; `load16_a2` at 1266) and its `apply`
is one `dp4a4(r.q, ld_q8_16(xb, r.half), 0)`; `Wide32Q6U` (native_mmvq.dp.cpp:2555-2566) is
the same shape with the two per-16 scales Q6_K keeps). The decode
`apply` becomes identical to `Wide32Q6U::apply` — load 16 signed bytes, one 16-byte activation
vec, 4 dp4a, scale by the two folded products:

```cpp
// per 16-value sub-block (one int4 of weights against one 16-byte Q8_1 half):
d * xb->ds[0] * (sum of 4 dp4a over the 16 signed bytes and the activation ints)
```

**Per-subblock ops (16 elements):** one 16-byte weight load (signed bytes, so no unpack), one
activation `ld_q8_16`, four STRATA_DP4A (native_mmvq.dp.cpp:2558-2566 mirrors this exactly),
two scale multiplies `d * ds`, one scalar sum. The dot is `dp4a` in the integer domain and the
scale `dot/sum` is applied as `d*ds*dp4a`, floating accumulate — `sum` is the dp4a accumulator,
not an added term (Q2_0 has no per-element offset, unlike the affine Q4_0/Q5_0 path with its
`- 4*ds.y()` correction, native_mmvq.dp.cpp:476-479). State is exact: the pre-unpack runs once
at weight load (as `native_q6k_preunpack_kernel`, native_mmvq.dp.cpp:2518), and every decode
reuses the same signed bytes without re-unpacking. To mirror the Q6U-style block one would store
`{float d; int8 qs[16]}` and four such blocks per Q2_0 super-block; `d` is uniform, so the finer
per-16 split only buys disjoint 16-byte loads, not precision.

## 4. Verdict on ~2x plausibility

**No ~2x.** Pre-unpacking is probably only a little.

The Q6_K win came from removing a genuinely heavy in-kernel unpack: `q6_q8_dot_impl` per dot
does the per-16 scale selection plus two mask-shift passes (`vil`/`vih`) and a signed-byte
gather via `vectorized_binary<sycl::char4>` with saturating subtract (native_mmvq.dp.cpp:679-693)
— the ISA showed dp4a was only 32 of 985 instructions *on the same ALU integer pipe* as the
bfn/xor/mov unpack (native_mmvq.dp.cpp:2499-2501), so eliminating that unpack doubled decode. Q2_0's in-kernel
unpack is a 2-bit field costing only the `byte_level_permute` pair per 16-bit word
(native_mmvq.dp.cpp:319-322); the block is already 2-bit dense and the decode is already
dp4a-shaped. Removing a couple of byte-permutes per chunk does not move a ~2x ALU cost, so the
pre-unpack path (`{float d; int8 qs[16]}` + `d*ds*dp4a`) buys at most a small constant-factor
improvement — and would spend GPU memory (4 signed bytes per 64 elements for data the block
already carries) with nothing near Q6_K's payoff to show for it. Feasible, but low value.
