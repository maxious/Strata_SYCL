"The was built without the matrix-MMA SPIR-V extension"
2026-06-03 · initial analysis
✗ DISPROVEN — byte-identical binaries
▶
The reasoning
Inspecting the shipped wheel, the device image contained but was missing and — symptoms of an build. In the matrix-MMA extension is declared only inside (gated on ), yet uses unconditionally. Conclusion at the time: a TLA-off build emits ops without declaring the capability → runtime can't lower them → throw.
Why it's wrong
The C++ API already emits by default. A built with the explicit flag is byte-identical to one built without it — the extra flag adds a different, unused extension. Both fail identically. No build flag, and no rebuild, changes the outcome.
Lesson
The string lives in (the DPC++ runtime) — not in ARK and not in the driver. That was the first clue the real determinant was the runtime, not the build. It took two more turns to act on it.

The fix & escape hatches
PRIMARY
Upgrade the runtime
Ship/link a DPC++ whose matrix includes (intel/llvm ≥ 2026-06-04, or a oneAPI release carrying that entry). No driver, IGC, or hardware change needed.
Caveat: SONAME bumps →; the consumer (torch-xpu / ARK ) must be built against it — no drop-in.
ESCAPE
Route m>1 through oneDNN
Send w4 m>1 through the oneDNN fp GEMM instead of the fused int8 kernel. oneDNN does its own DPAS codegen and never touches the gated op.
ESCAPE
Inline-dpas kernel
Replace ARK's int8 kernel with hand-written asm (à la ), or switch ARK to AOT (). Keeps fused int8 perf, removes all runtime sensitivity.
