Purpose

Int4 MoE decode on Xe2 spends most of its expert time in the fixed cost of cutlass_grouped_gemm_interface. At one decode token with top-8 routing each expert sees one row. On Qwen3.6-35B-A3B (GPTQ int4 experts), the 8 active experts of a layer are 13 MB of weights, about 21 us at the B70's bandwidth, but a gate_up call takes ~56 us and a down call ~34 us.

This PR adds torch.ops._xpu_C.moe_int4_gemv, a SYCL GEMV for the int4 layout the grouped GEMM already uses (int8-packed signed 4-bit [E, N, K/2] from implement_zp, per-group scales [E, N, K/G] in the activation dtype). XpuFusedMoe._apply_kernel routes int4 calls with at most 8 rows to it (INT4_GEMV_MAX_ROWS); larger calls (prefill, MTP verify, batched decode) keep the grouped GEMM. VLLM_XPU_FUSED_MOE_INT4_GEMV=0 turns it off.

Kernel: one work-group per (active expert, block of N). The work-group finds its expert with a group scan over rows_per_expert (no host sync, works under graph capture). Each sub-group computes 4 output columns for up to 2 rows at a time, lanes split K in chunks of 32 int4 values (16-byte weight loads), fp32 accumulation, per-group scale applied per chunk.

Related: #509 (fixed per-step MoE decode cost on the Arc Pro B70).

Related, not duplicates: #628 / #637 (fused routed + shared-expert decode for FP8 per-tensor weights) and #623 (FP8 decode GEMV). This PR covers int4 experts in the existing XpuFusedMoe path and does not touch those.

Test Plan

uv pip install --no-build-isolation -e .
.venv/bin/python -m pytest tests/fused_moe/test_grouped_gemm.py -k "moe_int4_gemv or int4" -v
.venv/bin/python -m pytest tests/fused_moe/test_fused_moe.py -k int4 -v   # m=1 and m=4 without bias now take the GEMV end to end
VLLM_XPU_FUSED_MOE_INT4_GEMV=0 .venv/bin/python -m pytest tests/fused_moe/test_fused_moe.py -k int4 -v

test_moe_int4_gemv checks the op against a dequantized fp32 reference and against cutlass_grouped_gemm_xe2 on the same inputs: Qwen3.6-35B-A3B shapes (w13 1024x2048, w2 2048x512) and 5120x8192, 16 and 256 experts, 1-8 rows with one or two rows per expert, bf16 and fp16.

E2E (vLLM main + this branch, one B70): Qwen3.6-35B-A3B-GPTQ-Int4 (palmfuture), single request, decode tok/s with VLLM_XPU_FUSED_MOE_INT4_GEMV=0/1, plus a short accuracy eval (gsm8k via lm_eval, 250 questions) for both.

Test Result

Measured 2026-10-15 on one Arc Pro B70 (b70 tab, testq 004). Kernel source = this branch (csrc/xpu/grouped_gemm/moe_int4_gemv.cpp and
vllm_xpu_kernels/fused_moe_interface.py from fad147a) applied to release/0.1.15.4, which is the vllm-xpu-kernels in the
vLLM nightly XPU image used (vllm 0.32.0rc1.dev190+g3f1bcfd82); the op was built as an _xpu_C library fragment instead of a
full rebuild. Not run: a full build of upstream main 6b30c9b.

pytest (installed package + this branch):

  • tests/fused_moe/test_grouped_gemm.py -k "moe_int4_gemv or int4": 46 passed. 6 more cases (n=5120, k=8192, e=256) ran out of memory in the test itself: it built the random int4 weights as int64 (~40 GiB) before converting. The test now generates them as uint8 and runs that shape with 16 experts only, like the existing cases for it (256 experts would still need ~10 GiB), so its 30 cases are exactly the shapes that passed above (the uint8 generation itself has not been run on a GPU yet).
  • tests/fused_moe/test_fused_moe.py -k int4: 40 passed (m=1 and m=4 without bias go through the new path).

E2E, vLLM nightly 3f1bcfd8 + this branch, palmfuture/Qwen3.6-35B-A3B-GPTQ-Int4, --language-model-only, fp8 KV, 4K context,
XPU graphs, no MTP, 1 request, 512-token answers, decode tok/s (code / prose):

VLLM_XPU_FUSED_MOE_INT4_GEMV decode tok/s gsm8k (first 100 test q, greedy, chat, no thinking)
0 (CUTLASS grouped GEMM) 75.8 / 76.3 97/100
1 (this PR) 86.6 / 87.2 (+14%) 97/100

With MTP (num_speculative_tokens=4, 2K context) and the GEMV on: 157.3 / 118.7 tok/s, no GPU faults in the kernel log. Not tested: other Intel GPUs (PVC, Xe3), expert parallelism.

Prior measurements of the same kernel, out of tree (vLLM v0.31.0 XPU image, kernel loaded as a separate extension and dispatched from XpuFusedMoe, one Arc Pro B70, palmfuture/Qwen3.6-35B-A3B-GPTQ-Int4, 1 request, 16K context, 512-token code / prose answers, decode tok/s; source: https://github.com/riceharvest/b70-qwen38-cookbook README, "Qwen3.6-35B-A3B (MoE)"):

no MTP MTP k=4
without the GEMV 78.7 / 79.1 183.9 / 134.3
with the GEMV 93.8 / 94.3 200.8 / 145.4
  • Per layer at 1 token: gate_up 56 -> 18 us, down 34 -> 14 us.
  • Matches CUTLASS to 3e-4 relative error per call (stress test: 900 routings including outlier activations; 500 replays inside an XPU graph). In serving, an eager cross-check of every decode call found 0 mismatches over 2,048 steps. Greedy GEMV vs CUTLASS per-step KL: p50 0.0001, p99 0.043, with divergences at near-ties, the same as CUTLASS graph vs eager.
  • 0/32 corrupted outputs with 8 concurrent long requests.

(Optional) Documentation Update

None (no user-facing option besides the env var, documented in fused_moe_interface.py).
