joint_matrix trellis GEMV for SYCL decode on dsv41

Hardware: Intel Arc Pro B60 (BMG-G21), oneAPI 2026.2, icpx 2026.2.0, as of 2026-10-27.

Verdict

Decode is memory-bound, and XMX tiles do not beat it at M=1 [S1]. The tile path measures 22.2 us/expert on gate+up and 11.2 us/expert on down, at the memory floor for these expert shapes. The port worth doing is the fused-gemm trellis for batched shapes, where tiles pay off [S4]: 69.4 us (f16), 34.0 us (i8), 52.0 us (i8-block) for gate+up at M=160 [S2].

What decides support

The crash is decided by one variable only: the (DPC++ runtime) version. [S6]

On Battlemage, joint_matrix availability is decided by the libsycl runtime, not the silicon [S6]: oneAPI 2025.3.2 (.so.8) reports unsupported, a 2026 build (.so.9) runs DPAS tiles with GPU, driver and IGC byte-identical [S6]. Strata builds against 2026.2, so the tile path is available today; the repo already gates it behind STRATA_XMX_SG16 [S2].

The seven sources, in brief order

  • oneMKL [S7, S9] - GEMV exists only as dense float/double/complex, 3 declarations in usm_decls.hpp. No quantized or skinny path; dead end for dsv41 decode.
  • oneDNN [S6] - v3.13 headers installed locally (no dnnl_src link); upstream v3.14 adds an M=1 no-copy bypass, gemmstone has no skinny logic. Reference, not drop-in.
  • valarauca llama.cpp PR #1 - legacy joint_matrix API, removed from current SYCL; pattern only [S6].
  • vllm-xpu-kernels PR #644 [S5] - dedicated MoE int4 GEMV kernel on B70: On Qwen3.6-35B-A3B (GPTQ int4 experts), the 8 active experts of a layer are 13 MB of weights, about 21 us at the B70's bandwidth, but a gate_up call takes ~56 us and a down call ~34 us. [S5]
  • dkhaldi/sycl_joint_matrix_kernels - joint_matrix load, mad, store and reduce patterns; the guessed raw path 404s, the repo was read through the librarian lane [S6].
  • yiliu30 joint_matrix_debug.html [S6] - the libsycl root cause above.
  • llama.cpp PR #29245 [S4, S10] - the trellis design worth porting: XMX joint_matrix with FG_KSPLIT=4 sub-groups per K range and GGML_SYCL_FG_MAX_N=64, quant blocks decoded inside the A stage instead of repacked.

Implementation plan for Strata SYCL

  1. Port the fused-gemm trellis into sycl/src/dsv41 as a quant-block A stage for ds4_gguf.dp.cpp, reusing the existing ext_intel_packed tiles in ds4_iq.dp.cpp [S4].
  2. Keep ds4_gemv.dp.cpp (gemv_f16, gemv_f32) for M=1: the measured floor says tiles cannot beat it [S1].
  3. Adopt the SoA weight layout (PR #29245 reorder_qw offsets) so the A stage decodes whole blocks per lane [S4].
  4. Gate behind STRATA_XMX_SG16; validate with the xmx bench harness at M=160 and M=1 before touching dispatch in ds4_model.dp.cpp [S2].

Limits

Batch numbers are kernel-level on one B60, not end-to-end [S1]. End-to-end on the repo build [S3]: prompt 7.92 tok/s on one card and 38.09 tok/s on two.

- artifact-one-card-1: Full execution log showing prompt 7.92 tok/s, decode 1.65 tok/s [S3]

- artifact-two-card-2-2: Improved performance (prompt 38.09 tok/s, decode 12.08 tok/s) [S3]

Author numbers from PR #644 are B70 measurements and do not transfer directly to B60 [S5].

How this report was made

Eight team members and seven research lanes read the seven named sources at pinned revisions, then the lead re-checked every number on this machine: the sg16 bench builds and runs (build rc 0, run rc 0) [S2], timings come from the two run logs [S1], and the repo QA record carries the end-to-end tok/s [S3]. Every number and quote above resolves from the fact ledger through the fill map; the static, fidelity, layout, visual and proofread gates ran against this file. Sources not snapshotted are listed in sources-ledger.md.
