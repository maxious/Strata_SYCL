# dsv41-sycl-dpct-and-xpu-test - Work Plan

## TL;DR (For humans)

**Who this is for and what changes for them:** The owner of this PC - two Intel Arc Pro B60 cards, 24 GB each - who wants Strata's DeepSeek dsv41 engine to answer a real question on the Intel cards. Today the engine starts, prints timings, and answers the same token over and over; after this work it answers "Paris" for "what is the capital of france", and the speed numbers printed beside it are real ones measured on this machine.

**What you'll get:** Five pieces, each built and run before it merged. The dpct conversion notes cleaned up so a reviewer can see what was reviewed and what was left alone; the two conversion classes that can actually be wrong checked and fixed; the card-side signalling settled by moving the answer through the copy engine instead of a store the card polls; the routing list the host reads made visible, which is what makes the host CPU lane contribute the experts the card does not hold; and a measured run on one card, then on both, with the answer quoted and the throughput taken from a prompt that completed.

**Why this approach:** The conversion sweep found no half-finished work left to redo - only two classes can be wrong, so the cleanup is a documentation pass plus two audits, not a rewrite. Correctness is chased before speed is reported, because the current output is a repeated single token, and a speed number beside a wrong answer is not evidence. One card runs new code first; the second card is only compared against a same-day run of the same build on the first.

**What it will NOT do:** It will not change any default - the Intel path stays behind its own switch, and NVIDIA and AMD builds are untouched. It will not rewrite kernels for speed hints nobody has measured. It will not report a tokens-per-second number from a run whose prompt never completed. It will not build the SYCL library of the upstream inference engine; the memory query is mirrored with attribution.

**Effort:** Large
**Risk:** High - the work is device-bound and the card has never been proven to see a store the host wrote; a wrong answer or a wedged card can hold a wave, and the guard is a bounded spin, not a proven doorbell.
**Decisions to sanity-check:** Two conversion classes are audited and the other ~730 notes are documented rather than acted on. The occupancy hint is A/B-tested through an existing switch instead of rewritten. The dual-card number is only claimed against a same-day single-card run of the same build.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No blanket conversion of the 156 DPCT1065 barrier hints: the barriers at `ds4_kernels.dp.cpp:2232/2237/2263` fence global host-mapped traffic, so narrowing them to local space is a regression hazard.
- No speculative perf rewrite of DPCT1110 register pressure, DPCT1013 rounding, DPCT1049 work-group size, DPCT1118 convergence, DPCT1124/1024 memcpy notes, or DPCT1078 fence ordering. Each is documented as accepted with its reason; DPCT1078's `acq_rel` matches `__threadfence()`/`__threadfence_system()` intent and the handshake values already bypass caches.
- No rewrite of the DPCT1007 occupancy site (`exl3.dp.cpp:1951-1953`, hardcoded `n = 2`). It is A/B-tested through `STRATA_GLM_EXL3_DECODE=legacy|new` and rectified only if a measurement shows the new family matters.
- No build of the upstream SYCL library (`ggml_sycl`). The card memory query mirrors the sysman path with attribution (`ds4_mem.hpp`, `ds4_model.dp.cpp:2087-2088`).
- No new abstraction, no new default, no new engine feature, no `.omo/` or `bench/results` commit.
- No throughput claim from a run whose prompt did not complete; no piped exit code reported as a result.

## Execution strategy
### Parallel execution waves
- **Wave 1 - baseline and conversion cleanup (todos 1-4).** Todo 1 is the baseline gate (no commit).
